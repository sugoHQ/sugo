# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Sugo is a Pomodoro timer for Linux desktops, at home on KDE Plasma: C++17 + Qt 6.8+ (extra-cmake-modules at build time only; no KDE Frameworks library: `Localization` replaces KI18n, `Settings` KConfig, `Notifier` KNotifications, QSystemTrayIcon KStatusNotifierItem), a Qt Quick UI drawn with its own components and theme, local SQLite storage. English only for now. `docs/DEVELOPMENT.md` is the authoritative dev guide (distro dependencies, Flatpak build, release checklist).

## Commands

```sh
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
cmake --build build
ctest --test-dir build --output-on-failure              # whole suite
ctest --test-dir build -R tst_timerengine --output-on-failure   # one test (QtTest binaries also accept a test function name when run directly)

# Same conditions as CI (no display, no session bus):
env -i PATH=/usr/bin:/bin HOME=/tmp/sugo-test-home ctest --test-dir build --output-on-failure

# Metadata validation (also run in CI)
appstreamcli validate --no-net data/stream.sugo.app.metainfo.xml
desktop-file-validate data/stream.sugo.app.desktop build/stream.sugo.app.runner.desktop  # generated by configure

# String template (the UI is English-only for now): regenerate po/sugo.pot
bash po/Messages.sh
```

The build must stay free of compiler warnings. There is no separate linter.

## Architecture

**Wiring lives in `src/main.cpp`.** It owns object lifetimes (declaration order is deliberate: database/repositories/inhibitor before the QML engine, helpers parented to a `services` QObject after it) and connects all services by signals. Several C++ classes are QML singletons (`QML_ELEMENT`/`QML_SINGLETON`: `TimerEngine`, `PresetModel`, `AppSettings`, `SilenceController`, `StatsModel`, `ScreenLockWatcher`, `Diagnostics`, `CalendarSync`, `UpdateChecker`); main fetches them via `engine.singletonInstance<>()` and then `attach()`es their dependencies, rather than constructing them itself. `DataManager` and `FocusSoundController` are exposed as context properties instead.

**Data flow centers on `TimerEngine`** (`src/core/TimerEngine.h` documents the full state machine). Remaining time is always `deadline - clock.now()` from an injectable `Clock` (monotonic), so ticks only drive UI refresh; tests use `tests/FakeClock.h`. Other components are observers of its signals:
- `TimerBinding` pushes the selected preset from `PresetModel` into the engine (switching preset resets; editing only reconfigures).
- `SessionRecorder` turns `sessionEnded` into rows via `SessionRepository`; `StatsModel`/`StatsAggregator` read them; `CalendarSync` listens for `workSessionRecorded` and uploads CalDAV events.
- `PhaseNotifier`, `SilenceController` (notification inhibit), `PowerInhibitor`, `ScreenLockWatcher`, `FocusSoundController`, `TrayController`/`TrayPresenter` react to state changes.
- External control: `DBusTimerService` adaptor at `/Timer`, `KRunnerService` at `/krunner`, both on the `stream.sugo.app` bus name, which `SingleInstance` also uses to forward second launches.

**Persistence is split:** presets and sessions are in SQLite (`src/db/`, `~/.local/share/sugo/sugo.db`); app preferences are a QSettings INI file (`~/.config/sugo/sugo.conf`, through `src/core/Settings.h`, which keeps the file mode 0600), used by `AppSettings` and `CalendarSync`. The calendar password goes to the desktop keyring through `SecretStore` (Secret Service over D-Bus), with the settings file only as a fallback; `CalendarSync` keeps its unsent-event queue there too, each event bound to the account it was queued for. `Database` tags its files with `PRAGMA application_id`, versions the schema with `PRAGMA user_version` and an ordered `migrations()` list in `Database.cpp` (append new migrations; never edit old ones), moves foreign/corrupt files aside, and refuses newer schemas. A file it cannot read (busy, locked) is never moved: `open()` fails and `main.cpp` falls back to an in-memory database. Repositories hold only the connection *name*. If the file can't be opened the app falls back to an in-memory DB. `PresetPersistence` loads presets into the model and saves every change synchronously.

**The interface** (`src/qml/`) uses Qt Quick Controls' Basic style, restyled: `Main.qml` (the window, which draws its own title bar, plus the quit, task-note and screen-unlock dialogs), `pages/`, and our components in `components/` (`SButton`, `STextField`, `ConfirmDialog` for every modal question, `Banner` for messages inside a page, `LineIcon` for the interface's own line icons, `ThemeIcon` for icons of the desktop's theme). Every colour and size comes from the `Theme` singleton (`src/qml/theme/Theme.qml`). Theme icons come from `ThemeIconProvider` (`src/platform/ThemeIcons.h`, registered in `main.cpp` as `image://icon/<name>`, `?color=<hex>` to paint a symbolic icon in one colour) and the `ThemeIcons.exists()` singleton, which lets `ThemeIcon.valid` say whether the theme has the icon.

**Platform abstractions:** notification inhibition goes through `NotificationInhibitor` with `FreedesktopInhibitor`/`NoopInhibitor` chosen by `InhibitorFactory`; tests substitute `tests/FakeInhibitor.h`. Notifications themselves go through `Notifier`: `FreedesktopNotifier` (org.freedesktop.Notifications over D-Bus, with KDE's inline reply where the server offers it) or `TrayNotifier` (a tray-icon message), chosen by `NotifierFactory`; tests substitute `tests/FakeNotifier.h`. KNotifications is not used: the end-of-phase sound is played by `AppSettings::playSoundPreview`, so there is no notifyrc. Autostart writes an XDG autostart entry, or under Flatpak asks the Background portal (`src/platform/Autostart.h`).

**Packages and updates:** the AppImage (`packaging/appimage/build.sh`, built by `.github/workflows/appimage.yml`) replaces itself: `UpdateChecker` reads the feed of the chosen channel (`stable.json` of the latest release, `nightly.json` of the rolling `nightly` pre-release, written by `release.yml` and `nightly.yml`), and, only when the user clicks "Install update", downloads next to the AppImage (`AppImage::path()`), verifies size and SHA-256, and swaps the file; the new version starts after "Restart to update". There is an AppImage for x86_64 and one for aarch64: the feed's top-level keys are the x86_64 file (what every installed version reads; never change their meaning), the arm64 AppImage reads only its `linux-aarch64` object and the macOS app its `macos` one (`AppImageInstaller::feedKeyFor()`). Flatpak and source builds only report updates. Branches: daily work on `dev` (CI only), `testing` publishes the nightly build, `main` holds what was tested and gets the release tags (`docs/DEVELOPMENT.md`, "Branches"). Nightly versions are `X.Y.Z-nightly.DATE.N` (`-DSUGO_VERSION`), pre-releases of the version in `CMakeLists.txt` (of the next patch once that one is released), so they sit between two releases.

## Adding files and tests

- All C++ code but `main.cpp` is compiled once into the static library `sugo_core` (`src/CMakeLists.txt`, which lists every source explicitly), which is also the QML module; the program links it plus its static QML plugin `sugo_qml` (imported in `main.cpp` with `Q_IMPORT_QML_PLUGIN`). A new source file goes in `sugo_core`'s `target_sources`; new QML files go in the `qt6_add_qml_module` `QML_FILES` list. `sugo_core` links Qt privately, so the program and each test name the Qt modules they use themselves.
- D-Bus is Linux-only: on macOS Sugo does not link QtDBus (`packaging/macos/build.sh` checks; the bundle still carries QtDBus.framework only because qt.io's QtGui links it). Sources that need it go in the `if(NOT APPLE)` block of `src/CMakeLists.txt` (or keep their D-Bus code under `#ifndef Q_OS_MACOS`, as `PowerInhibitor` and `ScreenLockWatcher` do), and a test built on both systems names `${SUGO_DBUS}` (empty on macOS) instead of `Qt6::DBus`.
- A new test needs a `sugo_add_test(tst_name <Qt modules it uses>)` line in `tests/CMakeLists.txt`. The modules decide what `QTEST_MAIN` creates: `Qt6::Widgets` a QApplication, `Qt6::Gui` a QGuiApplication (both need offscreen, below), else a QCoreApplication.
- Tests that create a GUI application set `QT_QPA_PLATFORM=offscreen` via `set_tests_properties`. D-Bus tests start a throw-away bus with `tests/PrivateDBus.h` (no service activation, so nothing installed on the machine is started) and must work (or skip) without a session bus.
- QML pages are covered by smoke runs (`tests/smoke_app.sh`): the real binary starts offscreen with `SUGO_SMOKE_PAGE=<page>` (or `SUGO_STATS_SMOKE_TEST=1`) and isolated XDG dirs; any QML warning fails the run (exit 30), and smoke-mode checks in `Main.qml` call `Qt.exit()` with a non-zero code on failure (e.g. 23-55 for the settings, welcome, presets and timer-page checks; 47: a message on the welcome tour's setup step moved the step; 54: the `inventory` run could not save its report; 56-59, 61: the Sync tab; 60: the data of Sugo 1.0.0 taken back at startup, `smoke_app.sh sugo100-db`; 64: a `NumberField` misread what was typed; 65: the composer of the welcome tour's last step; 66: the usage statistics switch, in the welcome tour and in Settings, missing or on by default; 67: a row of Settings or of the timer page whose controls take more than `Theme.settingsControlsMaxWidth`; 68: the break suggestion missing under the clock, or changed when the focus page came back). `tests/manual-review-checklist.md` covers what automation doesn't.
- Linux and macOS must offer the same: `tst_platform_parity` lists every screen's controls (smoke mode `inventory`) and compares them with `tests/platform-parity.json`. A control on one platform only must be listed there with its reason; one on both goes in `common` (`docs/DEVELOPMENT.md`, "Linux and macOS parity").

## Conventions

- User-visible strings use `i18n()` / `i18nc()` / `i18np()` / `i18ncp()` from `src/core/Localization.h` (KI18n-compatible, but KI18n itself is not used; the UI is English-only for now), never `tr()`. Compile definitions forbid implicit ASCII casts (`QT_NO_CAST_FROM_ASCII` etc.): use `QStringLiteral`/`QLatin1String`.
- QML uses only the colours and sizes of `Theme` (`src/qml/theme/Theme.qml`). `tests/check_qml_colours.sh` fails on any colour literal outside `Theme.qml` (only `"transparent"` is allowed); the tray icon's fixed colours live in `src/core/TrayIconStyle.h`, used by both `TrayController` and the welcome page's picture of the icon. `tests/check_qml_sizes.sh` fails on literal sizes of 2 px or more outside `Theme.qml`; allowed are 0/1 (no spacing, layout weights, 1 px borders) and artwork drawn in its own coordinates and scaled as a whole, between `// artwork-begin` and `// artwork-end`.
- The layout never moves when a message comes, goes or changes: put a message that may appear inside a page in a `MessageSlot` (a `Banner` in a place of fixed height that fades in and out, its text cut after `lines` lines), lay it over the content, or use the toast (`applicationWindow().showPassiveNotification()`); fade text with `opacity` rather than `visible`, give a description that changes with a state its `descriptionVariants` (`FormRow`, the settings' `SettingRow`) and a button whose label changes its `labels` (`SButton`).
- In QML, never name a property `onXxx` ("on" + capital letter: QML takes it for a signal handler), and never give anything `id: palette` (it collides with the `palette` property of Qt's controls).
- Every file carries an SPDX header (GPL-3.0-or-later for code, CC-BY-SA-4.0 for docs).
- One commit per change: each activity gets its own commit (a change to the title bar, a translation, a tweak to the timer are three commits), never unrelated work bundled in one.
- Commit messages and pull requests carry no `Co-Authored-By` line or other attribution to Claude.
- Releases: version must agree across `CMakeLists.txt` `project(... VERSION)`, the newest `<release>` in the metainfo XML, and the `vX.Y.Z` tag, or the release workflow refuses to publish. Follow the checklist in `docs/DEVELOPMENT.md`.

## Working with subagents

Subagents may be used for this repository. When spawning one, prefer the Haiku 5.5 model (`model: "haiku"`) unless the task clearly needs a stronger model.

Each Haiku 5.5 subagent has a budget of 100k tokens. The Agent tool has no hard token limit, so keep within it by:
- giving each subagent one narrow, well-scoped task, with the file paths it needs already in the prompt so it doesn't search broadly;
- telling it in the prompt that it must finish within 100k tokens, read only the parts of files it needs, and return a short answer;
- splitting larger work into several smaller subagents rather than one long-running one.
